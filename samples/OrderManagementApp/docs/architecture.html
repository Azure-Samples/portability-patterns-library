Order Management

One app, written for Azure, that runs on Azure with PaaS services and on Azure Local with everything on site, and keeps running there when the link to Azure drops.

Same app on both

One app definition and the same container images. Only the platform's Recipe Pack differs.

Works offline on site

Sign-in, images, certificates, credentials and monitoring stay on site.

Production patterns

Scoped service identities, TLS-protected backing services, replicated services, backups, retries and dead-lettering.

3. How an order is processed

  1. The user signs in and gets an access token with their roles (for example Orders.Create).
  2. The API checks the role, prices the order from the inventory service and returns 202 Accepted.
  3. The API publishes the order; the broker confirms it has it.
  4. The queue delivers the order to one of the processor's replicas.
  5. The processor reserves the stock with the inventory service, using its own token, not the user's.
  6. It archives the order as JSON in object storage.
  7. It records the order in SQL as Processed, or Rejected when stock ran out.

A failure partway is retried 5 times with backoff, then the queue redelivers the order. After 10 deliveries it moves to a dead-letter queue, and its stock is released unless the order was already recorded.

4. Key decisions

Declare capabilities, bind them per platform

Why: the same .NET containers run on AKS on both targets. The app says "a queue" and "a SQL database"; Radius Recipe Packs decide Service Bus or RabbitMQ. Moving platforms changes the pack, not the code.

Trade-off: each capability needs one Recipe per platform, kept to the same outputs.

Operators run the stateful services on site

Why: CloudNativePG and the RabbitMQ Cluster Operator replicate, fail over and back up, the job Azure PaaS does in the cloud. On the test site a PostgreSQL failover took about 26 seconds with no committed write lost.

Trade-off: operators to install and upgrade. Availability: standard runs one container of each instead, on smaller workers, with no backups.

Service Bus in Azure, RabbitMQ on site

Why: a durable broker separates order acceptance from processing. Azure manages Service Bus; RabbitMQ provides the local broker, with quorum queues in the default high-availability profile. Both sit behind IMessageQueue.

Trade-off: the app must handle redelivery and dead-lettered messages. Broker-specific features are not automatically portable.

SQL for orders, PostgreSQL for stock

Why: Azure SQL and local SQL Server keep the orders' SQL contract. Inventory owns its PostgreSQL schema, keeping stock updates and reservations behind one service.

Trade-off: two database engines to operate. Local SQL Server Express is a single instance without configured backups; PostgreSQL replication does not make SQL Server highly available.

Blob Storage or a local S3 archive

Why: the processor writes order JSON through IArchiveStore: Azure Blob Storage in the cloud, SeaweedFS's S3 API on site. The local object store also holds PostgreSQL backups.

Trade-off: object replication protects against a server failure, not losing the whole cluster. Copy archives and backups off site; the archive is not an immutable audit store.

Nothing at run time depends on Azure

Why: a site must keep serving users when its link drops. Images, sign-in, certificates, credentials and monitoring remain available on site, including the local Active Directory.

Trade-off: more to run on site; installs and upgrades still need the link.

Keycloak plays Entra's role on site

Why: users sign in with their Active Directory accounts; services exchange their Kubernetes token for a Keycloak token, the same pattern as Entra Workload ID. No stored secrets for the queue or service-to-service calls.

Trade-off: two identity providers, so a user's history doesn't move between platforms.

Least privilege for every service

Why: the API may only send, the processor only receive; only the inventory service touches stock; a one-off setup job is the only database administrator. Network policies let in only the traffic each service needs.

Trade-off: more identities and grants to set up; the scripts do it.

Designed for retries, not exactly-once

Why: reserving, archiving and recording are idempotent per order, so a redelivered order is safe. Failures retry, then dead-letter; stock is released only when the order store confirms the order was not recorded.

Trade-off: an order is accepted before it's processed; the browser polls for the outcome. An uncertain final outcome needs operator reconciliation.

Verified TLS and a site-owned certificate authority

Why: local broker, database and object-store connections use site-CA TLS with certificate verification, including replication traffic. The services call inventory over HTTPS and send telemetry to the collector over TLS, with certificates cert-manager issues for each Service name and renews on site; Keycloak connects to Active Directory over LDAPS.

Trade-off: distribute CA trust, protect its private key and monitor expiry. Kubelet health probes and traffic inside the monitoring stack stay plain HTTP within the cluster.

Ingress is the application's entry point

Why: the app declares one web route, not a platform-specific load balancer. AKS app routing or the site's NGINX ingress publishes the API and browser app over HTTPS; inventory and the processor remain internal services.

Trade-off: DNS, ingress availability and certificate trust are platform responsibilities. Calls between services carry their own TLS, from a CA the platform keeps in the cluster.

Credentials made and rotated on site

Why: local database passwords and S3 keys are generated on site and stored in Kubernetes Secrets, not fetched from Azure at run time. rotate-credentials.ps1 changes them using the cluster.

Trade-off: rotation is run by hand; restrict Secret access and back up the cluster's Secrets. Kubernetes Secrets are not, by themselves, a complete vault or rotation service.

Key Vault imports cloud secrets, not core credentials

Why: keep secrets already owned in Azure in Key Vault. The Secret Store extension uses a federated reader identity to sync selected values into Kubernetes Secrets, which consumers can read locally. Nothing is synced by default; the sample's database passwords and S3 keys stay site-generated.

Trade-off: refresh needs connectivity. During a disconnection only the last synced copy is available; cloud rotations and revocations do not propagate until the site reconnects.

A connected registry keeps images and Recipes local

Why: ACR remains the publishing source. Its read-only connected registry syncs selected images and OCI Recipes into the cluster, so kubelet and Radius can pull cached artifacts when the Azure link is down, rather than relying on a node's image cache.

Trade-off: provision local storage and sync every required repository before disconnecting. New versions and uncached artifacts still require connectivity.

Pinned versions, patched by PR

Why: every image and chart is pinned, so a restart never pulls something new. Dependabot raises a PR for each .NET and package security patch.

Trade-off: patches have to be merged and redeployed.

Monitoring on site, same signals

Why: the app emits OpenTelemetry once. On Azure it goes to Application Insights; locally Prometheus holds metrics, Loki logs and Tempo traces, with Grafana for investigation and alerts. Trace context follows an order across the services.

Trade-off: size storage and retention on site. Restrict Grafana to the operators' group because telemetry includes customer order details.

6. Scope

Two deployments, not a migration. Each platform starts with its own data. Moving a running workload between them (orders, stock, archives, users' history across Entra ID and Keycloak) is the next iteration.

  • Not yet highly available: SQL Server on Azure Local is a single instance with no backups configured.
  • Backups stay in the cluster: copy them off site for protection against losing the cluster.
  • A reference sample: size, secure and test it for your own workload.
